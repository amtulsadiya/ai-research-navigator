# ADR-005: Refusal Threshold — Data-Driven Cosine Similarity Cutoff

## Status
Accepted

## Date
2026-06-05

## Context
The system must refuse gracefully when retrieval confidence is low rather than hallucinating an answer. We need a threshold on the similarity score below which we refuse to generate.

The challenge: what value should this threshold be? Setting it too low means out-of-domain queries get answered (false positives). Setting it too high means legitimate AI queries get refused (false negatives).

## Decision
**Threshold = 0.525, derived from a 20-query evaluation dataset.**

## Evaluation methodology

Collected 10 valid AI/ML queries and 10 out-of-domain queries. Retrieved top chunk for each and recorded real cosine similarity scores (not RRF scores — see ADR-004).

Results:
```
Valid AI queries:   min=0.524, max=0.740, avg=0.649
Invalid queries:    min=0.457, max=0.585, avg=0.525
```

Tested every threshold from 0.450 to 0.750 in steps of 0.005 to find maximum accuracy:

```
Best threshold: 0.525
Accuracy: 90% (9/10 TP, 9/10 TN)
False positives: 1/10 (pizza query scores 0.585 — above threshold)
False negatives: 1/10 (borderline AI query scores 0.524 — below threshold)
```

## Why 0.525 and not higher
Raising to 0.59 would refuse the pizza query but would also refuse more legitimate AI queries (the false negative rate increases). 0.525 is the mathematically optimal point on this 20-query dataset.

## Known limitation
The false positive (pizza scoring 0.585) occurs because the Llama 2 paper contains human preference examples including food opinions — so "pizza" finds nearby vectors in the RLHF embedding space. This is a corpus contamination issue, not a threshold issue.

## Primary mitigation
The M3 router classifies queries as `out_of_scope` BEFORE retrieval. Pizza is correctly classified as out-of-scope and goes to the fallback node — never reaching the similarity threshold check. The threshold is a backup safety net, not the primary classifier.

## Re-evaluation plan
Threshold will be re-evaluated in M4 with the full 40-question golden set. Results documented in eval/report.md.

# ADR-006: LangGraph Agent Design — Linear Graph with Conditional Routing

## Status
Accepted

## Date
2026-06-05

## Context
We need an agent layer that routes queries to specialised sub-pipelines. The options are:

1. Simple if/else routing in Python
2. LangGraph state machine
3. ReAct agent with tool use
4. Multi-agent system

## Decision
**LangGraph StateGraph with explicit TypedDict state and conditional edges. Maximum 2 hops per query (router → handler → END).**

## Why LangGraph over simple if/else

| Property | if/else | LangGraph |

| Visualisable | ❌ | ✅ (Mermaid diagram) |
| State explicit | ❌ | ✅ (TypedDict) |
| Serialisable | ❌ | ✅ (JSON) |
| Observable | ❌ | ✅ (per-node logging) |
| Extensible | Hard | Easy (add node + edge) |
| Testable | Hard | Easy (mock state) |

## Why 2 hops (not more)
Deeper graphs add latency without benefit for our use case. Every query type has a fixed handler — there's no need for iterative refinement or back-and-forth between nodes.

## State design
`AgentState` is a TypedDict with `total=False` — all fields optional. Nodes only write the fields they produce. This prevents accidental coupling between nodes.

## Tool calls
Two tools implemented as LangChain `@tool` functions:
- `corpus_metadata_lookup`: used by FindPapers to search Qdrant by metadata without semantic search
- `get_current_year`: used by RecentDevelopments for date math (computing "last 12 months" cutoff)

Required by assignment: "at least one tool call within an agent node."

## Router fallback
If Gemini API fails during routing, the router defaults to `concept_explanation`. This ensures the system degrades gracefully rather than crashing.

## Consequences
- Every query takes exactly 2 hops — predictable latency
- State is inspectable at every step for debugging
- Graph is visualised in docs/adr/graph_visualization.md
- New routes can be added by adding one node + one edge without touching existing code
